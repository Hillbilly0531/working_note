## 经验卡片

### Skill 触发与日志目录唯一

**属性**：

- 分类：`#experience/cursor`
- 来源项目：[[working_note]]
- 相关主题：[[working_note]]
- 适用频率：高

**适用场景**：

- 发现 Agent 有时不写日志，或日志散落在多个目录。

**问题信号**：

- 项目内技能与全局技能指向不同输出路径；`description` 只描述流程不描述「何时用」。

**处理方法**：

- 统一唯一权威落盘路径：`setting/leyo/working_note/{YYYY-MM-DD}.md`；全局与仓库技能保持同步。
- Skill 的 YAML `description` 用「Use when …」列触发条件，避免 Agent 只读描述跳过正文。

**验证方式**：

- 抽查两轮对话后日志文件是否在预期路径生成或追加。

> [!warning] 踩坑提醒
> 不要用 `.working_logger` 作为正式目录；旧文档残留易导致「以为写了但其实写到别处」。

### Java 类型不匹配批量清零

**属性**：

- 分类：`#experience/java`
- 来源项目：[[working_note]]
- 相关主题：无
- 适用频率：中

**适用场景**：

- 大批量 `String`/`Integer`、`List` 泛型与 setter 入参不一致的编译错误。

**问题信号**：

- IDE `severity=8`；`setYsbProviderId`、Mapper 参数等与字段声明类型不一致。

**处理方法**：

- 先从 README 或诊断清单抽取错误列表，再按「Controller → Service → Mapper」或按错误类型分批改，每批改完跑一次 IDE 诊断 focal 文件。

**验证方式**：

- IDE ERROR 清零；Maven 不可用时明确写「仅 IDE 诊断 / 私服 401 阻断」而非声称全量编译通过。

> [!warning] 踩坑提醒
> 不要漏掉「警告仍为 Warning」与「本批 ERROR 已清零」的区分，避免误判为全部干净。

### 构建被私服阻断时的验证表述

**属性**：

- 分类：`#experience/debugging`
- 来源项目：[[working_note]]
- 相关主题：无
- 适用频率：中

**适用场景**：

- `mvn` 因 `401 Unauthorized`、父 POM 无法解析等无法完成全量构建。

**问题信号**：

- 日志或控制台出现私服鉴权失败；依赖解析停在父工程。

**处理方法**：

- 在工作日志「验证结果」中写：已执行什么（如 IDE 诊断）、未执行什么（全量 `mvn`）、阻断原因（401 / 父 POM）。

**验证方式**：

- 记录具体命令与错误摘要一行；能本地跑的用 `mvn -DskipTests compile` 等补充。

> [!warning] 踩坑提醒
> 绝不能把「代码看起来对」写成「构建已通过」。

- [[2026-05-08#15:41 - 修复 README 中 Java 类型报错]]

### 需求与接口类文档的验收口径

**属性**：

- 分类：`#experience/docs`
- 来源项目：[[working_note]]
- 相关主题：无
- 适用频率：中

**适用场景**：

- 写前端对接、测试用例拆解、技术规格评审类文档。

**问题信号**：

- 字段含义、版本号、边界条件、未确认项散落在对话里未落文档。

**处理方法**：

- 文档中固定写清：字段枚举/默认值、接口路径与版本占位、与代码对象字段对齐方式；未完成项单独列为「待确认」。

**验证方式**：

- 自检清单：与 Controller/DTO 字段名一致；读者能否按文档写请求与断言。

> [!warning] 踩坑提醒
> 版本号（如 `pv2980`）未定时须在备注标明，避免前端按错误版本联调。

### 产品文档转技术规格的通用提示词

**属性**：

- 分类：`#experience/docs`
- 来源项目：[[working_note]]
- 相关主题：无
- 适用频率：高

**适用场景**：

- 产品写的 PRD 需要交给 AI 或真人开发执行；需要将自然语言需求转化为结构化技术规格。

**问题信号**：

- 文档里全是"选中XX显示YY"、截图依赖 TAPD 外链、if/else 散落在段落中、前后端逻辑混在一起。

**处理方法**：

- 使用分层转化提示词：概述→数据模型→校验规则→API接口→业务规则；所有条件必须显式化为矩阵/枚举；不确定处用 TODO 占位而非编造。

**验证方式**：

- 自检：开发者拿到文档后能否直接知道"改哪里、怎么改、如何验收"；AI 能否直接生成代码骨架。

> [!warning] 踩坑提醒
> 不要试图一次性把"产品语言"完美转成"代码"，中间必须有一层"技术规格"作为契约，否则 AI 会过度推断或遗漏边界。
