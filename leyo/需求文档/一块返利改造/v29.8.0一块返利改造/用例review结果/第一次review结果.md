## 四、逐项问题说明

### 1. 高危：`break` 后存在不可达日志，存在编译失败风险

**是否修复：否**

在 `ReceiveShareServiceImpl.calShareAmount` 的数量阶梯处理分支中，`break;` 后面仍然保留了日志语句，Java 编译时可能报 `unreachable statement`。

风险：

- 直接导致代码无法通过编译
- 本次每满 X 件改造主路径受影响

建议：

- 将日志移动到 `break` 前
- 或删除该日志

---

### 2. 高危：每满 X 件 + 分层阶梯未按测试用例接入业务主链路

**是否修复：否**

测试用例 `L-1175795-04` 要求：

- 每满 X 件
- 分层阶梯
- 协议总体按分级阶梯累计求和
- 返利商品按最高阶梯计算

当前代码虽然新增了 `RebateEveryFullXCalculator.calcFullXGrade(...)`，但未看到该能力接入实际计算链路。

并且 `calNormalRebate` 中对于：

- `countType == "1"`
- `rebateRule == 1`

的场景，没有进入分级阶梯总额计算分支。

风险：

- 分层阶梯场景会算错
- `L-1175795-04` 无法通过

建议：

- 针对 `countType=分层` 且 `rebateRule=每满X件` 场景，单独补齐协议总体维度的分级公式计算逻辑
- 明确“协议总体走分层、返利商品走最高阶梯”的分支策略

---

### 3. 高危：指定批次数量型每满 X 件未生效

**是否修复：否**

测试用例中普通型与指定批次都要求区分计退口径，且拆解方案中也要求商品/批次限制支持 `perX`、`rebateAmount` 字段。

但当前指定批次分支仍然仅按 `rebatePrice` 计算：

- 未按 `rebateRule` 区分“每 1 件”与“每满 X 件”
- 未使用 `perX`
- 未使用 `rebateAmount`

风险：

- 指定批次数量型每满 X 件返利结果错误
- 对应测试用例无法通过

建议：

- 指定批次数量型分支也要按 `rebateRule` 分流
- `rebateRule=1` 时，使用指定批次对应的 `perX/rebateAmount` 计算

---

### 4. 警告：协议总体每满 X 件存在“逐明细 ROUNDDOWN”口径风险

**是否修复：否**

测试用例强调：

- 先确定命中阶梯
- 再按总体数量/金额代入公式
- 最终返利总额可能再拆分到明细

当前实现中，存在按分摊后明细逐条 `ROUNDDOWN` 的迹象。该方式在多条明细合计时会出现：

- `ROUNDDOWN(4/5)+ROUNDDOWN(5/5)=1`
- 但 `ROUNDDOWN((4+5)/5)=1`

某些场景结果相同，但更多情况下会出现总量口径与逐明细口径不一致的问题。

风险：

- 协议总体返利金额与测试用例断言不一致
- 在多明细分摊场景下少返或错返

建议：

- 协议总体 `limitType=1` 的每满 X 场景，先按总体数量计算总返利，再做分摊
- 不要直接对每条分摊后的明细独立做 `ROUNDDOWN`

---

### 5. 警告：一块销售数量不计销退逻辑虽已接入，但和需求口径仍需确认边界

**是否修复：部分修复**

当前代码中：

- 销售型先插入销售明细
- 若是一块，则不再追加销退明细

这说明“一块销售数量不计销退”的主逻辑已经接入。

但仍需确认两点：

1. 产品/测试文档中“一块销售数量”是否始终只能是不计退口径；
2. 非一块帝豪侧“销售出库 - 销退入库”的实现是否完全依赖负数销退明细，需联调确认。

建议：

- 和需求方确认“一块销售数量协议”的真实限制条件
- 增加对帝豪销退扣减口径的专项单测

---

### 6. 警告：一块判定口径与拆解方案不完全一致

**是否修复：否**

当前一块判定逻辑为：

1. 优先读配置 `leyo.boot.yikuai-provider-identities`
2. 否则用 `rawReturnRule != null` 推断是否一块

但拆解方案建议按 `provider_type = 3` 判定。

风险：

- 漏配配置时误判
- 历史脏数据导致误判
- 一块/非一块分流口径不稳定

建议：

- 优先基于可靠业务字段（如 `provider_type=3`）识别一块
- 配置和历史字段推断只作为兼容兜底

---

### 7. 建议：每满 X 参数缺失时仅运行期抛异常，可观测性不足

**是否修复：否**

当前 `RebateEveryFullXCalculator` 对：

- `perX <= 0`
- `rebateAmount <= 0`

会直接抛 `IllegalArgumentException`。

这可以保护计算正确性，但在生产任务中，若是同步数据缺失、镜像表字段为空，现场排查成本会较高。

建议：

- 在进入每满 X 计算前，补充业务日志
- 日志至少包含：`providerId`、`receiveBillCode`、`limitType`、`goodsBillSn`
- 必要时写入运行日志或异常链路，而不只是抛普通运行时异常

## 七、建议新增验证用例

建议优先补以下单测/联调用例：

1. **采购数量 + 每满X件 + 分层阶梯 + 计退**
   - 对应 `L-1175795-04`

   - 验证 `perX/rebateAmount` 是否真正生效
3. **协议总体多明细分摊场景**
   - 如数量 `4 + 5`，`perX = 5`
   - 验证是否先按总量算，再分摊
4. **一块销售数量 vs 帝豪销售数量回归测试**
   - 验证一块不计销退、帝豪扣销退
5. **参数缺失场景**
   - `perX` 为空
   - `rebateAmount` 为空
   - 验证错误日志是否可追踪

## 八、最终结论

本次需求代码修改**还不能判定为完全满足测试用例要求**。

目前主要属于：

- **计退分流能力已接入一部分**
- **数量型每满 X 件普通场景已开始接入**
- **但分层阶梯、指定批次、总体口径、判定口径等关键点仍未完全闭环**

建议在完成 P0 修复后，再进行第二轮 Review。
