### P0-1 修复 `break` 后不可达代码

#### 问题说明

`ReceiveShareServiceImpl.calShareAmount` 的数量阶梯分支中，`break;` 后还有 `log.info(...)`，存在 Java 编译失败风险。

#### 修复范围

- 文件：`lunar-rebate-service-core/src/main/java/com/leyo/lunar/rebate/core/service/bizservice/rebate/impl/ReceiveShareServiceImpl.java`
- 方法：`calShareAmount`

#### 修复要求

将阶梯命中日志移动到 `break` 前，或删除不可达日志。

#### 验收标准

- 代码不存在 `break`、`return`、`throw` 后仍执行普通语句的情况；
- 编译不再报 `unreachable statement`；
- 保留必要日志时，日志仍能打印：`receiveBillCode`、`limitKey`、`totalAmount`、`lower`、`upper`、`rebatePrice/perX/rebateAmount`。

#### 建议状态字段

### P0-2 补齐每满 X 件 + 分层阶梯主链路

#### 问题说明

测试用例 `L-1175795-04` 要求：

- 每满 X 件；
- 分层阶梯；
- 计退；
- 协议总体按分级阶梯求和；
- 返利商品按最高阶梯计算。

当前代码中虽然新增了 `RebateEveryFullXCalculator.calcFullXGrade(...)`，但业务主链路没有接入。

#### 修复范围

重点关注：

- `ReceiveShareServiceImpl.calNormalRebate`
- `ReceiveShareServiceImpl.calShareAmount`
- `RebateEveryFullXCalculator.calcFullXGrade`
- `RebateLimitService` / `RebateLimitDao` 中获取阶梯配置的相关方法

#### 修复要求

当同时满足以下条件时：

- `countType == 分层阶梯`
- `rebateRule == 每满X件`
- `rebateType == 数量`

需要新增专门分支处理。

建议逻辑：

1. 对协议总体 `limitType=1`：
   - 获取协议总体阶梯列表；
   - 按阶梯上下限、`perX`、`rebateAmount` 计算总返利；
   - 使用分级公式累计求和；
   - 再按明细进行分摊或回写。
2. 对返利商品 `limitType=3/7`：
   - 保持最高阶梯逻辑；
   - 但需要支持 `perX/rebateAmount`。

#### 对应用例

- `L-1175795-04`

#### 验收标准

- 分层阶梯每满 X 件时不再跳过分级计算；
- `calcFullXGrade` 或等价逻辑在业务主链路中被调用；
- 协议总体返利金额符合测试用例公式：
  - 所属阶梯返利 = `ROUNDDOWN((min(采购数量, 所属阶梯上限) - 下一级阶梯上限) / X) × 返利金额`
  - 下级阶梯返利 = `((阶梯上限 - 下一级上限) / X) × 返利金额`
- 返利商品仍按最高阶梯计算。

#### 建议状态字段

- 修复状态：待修复
- 验证状态：待验证

### P0-3 修复指定批次数量型每满 X 件计算

#### 问题说明

当前指定批次数量型分支只使用 `rebatePrice`：

- 未区分 `rebateRule=每1件` 和 `rebateRule=每满X件`；
- 未使用 `perX`；
- 未使用 `rebateAmount`。

这会导致指定批次数量型每满 X 场景计算错误。

#### 修复范围

重点关注：

- `ReceiveShareServiceImpl.calShareAmount` 中 `limitType == 7` 的数量型分支；
- `RebateReceiveDetailService.selPointBatchReceiveAmtByReceiveBillCode`；
- `RebateReceiveDetailMapper.xml` 对应 SQL；
- `RebateReceiveDetail` / DTO 中是否已承载 `perX`、`rebateAmount`。

#### 修复要求

指定批次数量型分支需要按 `rebateRule` 分流：

1. `rebateRule != 每满X件`：
   - 保持原 `shareAmount × rebatePrice`。
2. `rebateRule == 每满X件`：
   - 获取当前指定批次对应的 `perX`、`rebateAmount`；
   - 使用 `ROUNDDOWN(min(计返数量, 阶梯上限) / perX) × rebateAmount`；
   - 明确阶梯上限来源。

#### 对应用例

- 指定批次数量型每满 X 扩展场景；
- 与 `1175795` 数量型计算用例关联；
- 与 `1175801` 指定批次计退/不计退取数口径关联。

#### 验收标准

- 指定批次数量型 `rebateRule=1` 时不再使用 `rebatePrice` 直接相乘；
- SQL 或 DTO 能取到 `perX/rebateAmount`；
- 缺失 `perX/rebateAmount` 时有明确异常和上下文日志。

#### 建议状态字段

- 修复状态：待修复
- 验证状态：待验证

### P0-4 修正协议总体每满 X 件计算粒度

#### 问题说明

测试用例要求每满 X 件公式基于总体数量或所属阶梯数量计算：

`ROUNDDOWN(min(数量, 所属阶梯上限) / X) × 返利金额`

当前代码有按分摊明细逐条计算的风险，会导致多明细场景下总金额偏差。

#### 修复范围

重点关注：

- `ReceiveShareServiceImpl.calNormalRebate`
- `ReceiveShareServiceImpl.calShareAmount`
- `ReceiveShareServiceImpl.cntShareReceive`
- `ReceiveShareServiceImpl.receiveShare`

#### 修复要求

对于协议总体 `limitType=1` 的每满 X 件：

1. 先汇总用于计返的总体数量；
2. 根据总体数量命中阶梯；
3. 使用总体数量计算总返利金额；
4. 再按明细占比分摊回写。

不要在每条分摊明细上独立执行 `ROUNDDOWN(shareAmount / X)`。

#### 对应用例

- `L-1175024-03`
- `L-1175024-05`
- `L-1175795-02`
- `L-1175795-03`
- `L-1175795-04`

#### 验收标准

建议构造如下用例验证：

- 总数量：9
- 明细数量：4、5
- `perX=5`
- 预期：按总量 `ROUNDDOWN(9/5)=1`
- 不允许因逐明细导致错误总额

再构造：

- 总数量：11
- 明细数量：4、4、3
- `perX=5`
- 预期：按总量 `ROUNDDOWN(11/5)=2`
- 逐明细会得到 0，必须避免。

#### 建议状态字段

- 修复状态：待修复
- 验证状态：待验证

### P1-1 明确一块销售数量计退边界并补测试

#### 问题说明

当前代码对一块销售型逻辑为：

- 只插入销售明细；
- 不追加销退明细。

这基本符合“一块销售数量不计销退”的方向，但测试文档中存在“计退不为空”的表述，需要进一步确认真实产品口径。

#### 修复范围

重点关注：

- `RebateReceiveDetailService.calRebate`
- `RebateReceiveDetailService.calRebateV2`
- `RebateRuleNormalizeService.normalize`

#### 修复要求

1. 和产品/需求确认：一块销售数量协议是否永远不计销退；
2. 若确认是，则在代码注释和测试用例中固化；
3. 若并非永远不计退，则需要按 `returnRule` 进一步分流。

#### 对应用例

- `L-1175024-01`
- `L-1175024-02`
- `L-1175024-03`
- `L-1175024-05`

#### 验收标准

- 一块销售数量：按销售出库数量命中和计返；
- 帝豪销售数量：按销售出库命中，计返扣销退；
- 两类场景均有单测或联调数据覆盖。

#### 建议状态字段

- 修复状态：待确认
- 验证状态：待验证

### P1-2 收敛一块子公司判定口径

#### 问题说明

当前一块判定逻辑：

1. 优先配置 `yikuai-provider-identities`；
2. 其次用 `rawReturnRule != null` 推断。

但拆解方案建议按 `provider_type=3` 判断。

#### 修复范围

重点关注：

- `RebateRuleNormalizeService.isYikuai`
- `LunarLeyoBootProperties.yikuaiProviderIdentities`
- 供应商/子公司权限或认证相关模型与同步逻辑

#### 修复要求

建议判定优先级调整为：

1. 优先使用同步后的可靠一块标识，如 `provider_type=3`；
2. 配置 `yikuai-provider-identities` 作为临时白名单或兜底；
3. `rawReturnRule != null` 仅作为历史兼容，不作为主要判断依据；
4. 发生兜底命中时打印可追踪日志。

#### 验收标准

- 一块与非一块不会因 `returnRule` 历史脏数据误判；
- 配置缺失时仍能通过可靠业务字段识别；
- 兼容逻辑有日志可查。
