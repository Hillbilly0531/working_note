## 一、需求背景和必要性

### 1. 需求背景和描述（必填）

集采控销业务中，供应商给到乐药的费用除返利（正常返利、预收返利、集采代收）外，还有**非返利**（营销费、其他）部分。当前非返利的申请审核动作均在 OA 系统中完成，未与 PMS 打通，导致部分营销费被子公司当作返利费用使用。

**目标**：在 PMS 中对非返利资金进行全生命周期统一管理，打通**备案 → 使用 → 核销**全链路，并与返利凭证系统对接实现冻结/解冻/核销记录同步。

### 2. 技术方案目标（必填）

1. **全链路覆盖**：外部引入、内部分配、年度预算三种备案类型均支持完整的备案→使用→核销闭环
2. **金额准确性**：10+种金额状态（入账金额、已备案、已冻结、剩余可使用、已使用、剩余可核销、已核销等）的计算口径正确，不可超卖/超用
3. **查询性能**：汇总 TAB 在多维度筛选（厂牌池、项目、备案类型、部门、时间）下，响应时间 < 3秒
4. **返利凭证同步**：外部引入资金正确触发返利凭证的冻结/解冻/核销记录同步，不遗漏、不重复
5. **审批流程**：按部门+金额层级自动匹配审批人，17种待办类型覆盖到位
6. **自动调配**：使用/核销超出时自动从公共项目池调配金额，不阻塞用户操作

### 3. 必要性/业务价值评估（选填）

**市场必要性**：非返利资金（营销费）是供应商激励体系的重要组成部分，当前在 OA 中管理导致与 PMS 数据割裂，无法形成统一的费用视图，影响管理层决策效率。

**企业发展必要性**：将非返利管理纳入 PMS，实现费用数据统一管控，避免营销费被误用为返利，提升资金使用效率与财务合规性。

## 二、实现方案设计

### 方案一：领域驱动设计 + 事件驱动架构（推荐方案）

#### 1.1 方案概述关键点（必填）

以领域驱动设计（DDD）思想，在 **pms-rebate 单体应用**内按业务边界拆分为三个子域（Java package），通过 Spring 事件机制实现跨域协作，金额计算采用快照表避免复杂 SQL 实时聚合。

**三个子域划分**：

```
pms-rebate（同一个 Spring Boot 单体应用）
│
├── module/fundpool/record/      ← 备案子域
│   ├── RecordController.java
│   ├── RecordService.java       ← 备案状态机：草稿→待审核→已备案→作废/调配
│   ├── RecordRepository.java
│   ├── RecordEntity.java
│   └── event/RecordApprovedEvent.java
│
├── module/fundpool/usage/       ← 使用子域
│   ├── UsageController.java
│   ├── UsageService.java        ← 使用状态机：草稿→使用审核中→已使用
│   ├── UsageRepository.java
│   ├── UsageEntity.java
│   └── event/UsageApprovedEvent.java
│
└── module/fundpool/writeoff/    ← 核销子域
    ├── WriteoffController.java
    ├── WriteoffService.java     ← 核销状态机：草稿→核销审核中→已核销→冲红
    ├── WriteoffRepository.java
    ├── WriteoffEntity.java
    └── event/WriteoffApprovedEvent.java
```

**关键点**：

- 三个子域在同一单体应用内的三个 package，不拆微服务
- 跨域联动通过 Spring `ApplicationEventPublisher` + `@EventListener` 实现，不引入 MQ
- 金额快照表（`fund_pool_snapshot`）实时维护，汇总快照表（`fund_pool_summary`）异步更新

**（2）流水表归档与结转机制**

资金池业务需要保留完整资金变动链路，因此建议新增一张统一流水表 `fund_pool_ledger`，作为所有金额变更的审计账本。备案、使用、核销、冲红、释放、自动调配、返利凭证冻结/解冻同步等动作均落一条流水。快照表和汇总表只承担读模型职责，最终对账来源以流水账为准。

| 表名                               | 作用                       | 数据特征         | 生命周期                 |
| -------------------------------- | ------------------------ | ------------ | -------------------- |
| `fund_pool_ledger`               | 当前期流水表，记录近 12\~24 个月资金变动 | 高频写入、按时间持续增长 | 在线查询、对账、问题追溯         |
| `fund_pool_ledger_archive_yyyy`  | 年度归档流水表                  | 低频查询、只读      | 历史审计、财务追溯            |
| `fund_pool_carry_forward`        | 结转批次表                    | 每个结转周期一批     | 记录期初/期末余额、结转状态、操作人   |
| `fund_pool_carry_forward_detail` | 结转明细表                    | 每个资金维度一条     | 记录各资金池维度的期末余额与下期期初余额 |

流水表核心字段建议：

```sql
id                  BIGINT
biz_no              VARCHAR(64)   -- 业务单号：备案单/使用单/核销单/调配单/冲红单
biz_type            VARCHAR(32)   -- RECORD/USAGE/WRITEOFF/ADJUST/RELEASE/REBATE_SYNC/CARRY_FORWARD
record_id           BIGINT        -- 关联备案单ID，可为空
pool_key            VARCHAR(128)  -- 厂牌池+项目+部门+备案类型等维度生成的唯一键
occurred_at         DATETIME      -- 业务发生时间
amount_type         VARCHAR(32)   -- 金额科目：RECORDED/FROZEN/AVAILABLE/USED/WRITE_OFF/RELEASED
change_direction    VARCHAR(8)    -- IN/OUT，表示增加或减少
amount_notax        DECIMAL(18,2) -- 本次变动金额，不含税，金额为正，方向由 change_direction 表示
amount_tax          DECIMAL(18,2) -- 本次变动金额，含税
balance_after       DECIMAL(18,2) -- 当前金额科目变动后余额，便于审计追溯
ledger_period       CHAR(6)       -- 所属账期，如 202605
archive_status      TINYINT       -- 0未归档、1已归档
idempotent_key      VARCHAR(128)  -- 幂等键，防止重复入账
created_at          DATETIME
```

**归档策略**：

1. **按账期归档，不按单据状态随意搬迁**：以 `ledger_period` 为归档边界，建议保留最近 12\~24 个月在线流水，超过保留期且账期已关闭的数据归档。
2. **归档只搬流水，不搬业务主单**：备案单、使用单、核销单主表仍保留必要索引和状态；历史明细查询时按账期路由到归档表。
3. **归档前必须完成对账**：归档账期内流水合计、快照余额、汇总余额必须一致；不一致则阻断归档并生成异常任务。
4. **归档后只读**：归档表禁止业务写入。如历史单据发生冲红/调整，不修改旧归档流水，而是在当前账期新增一条反向调整流水。
5. **索引按查询场景设计**：当前表建议建立 `(pool_key, ledger_period)`、`(biz_no, biz_type)`、`(record_id, occurred_at)`；归档表重点保留 `(biz_no, biz_type)`、`(pool_key, ledger_period)`。

**结转策略**：

1. **年度结转为主，月度关账为辅**：每月可做账期关闭和汇总固化；每年做一次正式结转，生成下一年度期初余额。
2. **结转不是删除历史，而是生成期初流水**：对每个仍有余额的资金维度、金额科目生成 `CARRY_FORWARD` 流水，写入新账期/新年度，金额等于上期期末余额。查询新账期余额时以期初流水 + 新账期发生额计算，避免和历史账期重复累计。
3. **期末余额来自快照，流水用于校验**：结转时先从 `fund_pool_snapshot` / `fund_pool_summary` 读取各金额科目余额，再用 `fund_pool_ledger` 按 `pool_key + amount_type` 聚合校验。校验通过后写入 `fund_pool_carry_forward_detail` 和新账期期初流水。
4. **结转后旧账期冻结**：旧账期不允许新增普通业务流水；若出现历史补录或冲红，通过当前账期调整流水体现，并记录关联原业务单号，同时重算当前账期之后的快照/汇总。
5. **幂等执行**：结转批次用 `period + pool_key + carry_forward_type` 做唯一约束，重复执行只能重试未完成批次，不能重复生成期初余额。

推荐执行流程：

```
月度关账/年度结转任务
  → 锁定账期，禁止该账期新增业务流水
  → 聚合流水并校验快照/汇总余额
  → 生成结转批次 fund_pool_carry_forward
  → 按 pool_key 写入 fund_pool_carry_forward_detail
  → 对仍有余额的维度和金额科目写入下一账期 CARRY_FORWARD 流水
  → 更新下一账期快照/汇总表
  → 将旧账期流水 archive_status 标记为可归档
  → 归档任务搬迁到 fund_pool_ledger_archive_yyyy
```

**一期建议范围**：先实现流水表、账期字段、幂等键、按账期查询和年度结转批次表；归档任务可以先预留表结构和归档状态，待数据量达到阈值后启用自动归档。这样不会影响一期交付，又能避免后续流水表无限膨胀后再补架构。

**（3）金额一致性保障（四层兜底）**

| 层级  | 场景             | 保障方式                                                          |
| --- | -------------- | ------------------------------------------------------------- |
| 第一层 | 同一模块改金额（如使用申请） | DB事务 + `SELECT ... FOR UPDATE` 行锁，强一致                         |
| 第二层 | 跨模块联动（如核销触发释放） | 本地消息表 + `@TransactionalEventListener(AFTER_COMMIT)` 异步，保证最终一致 |
| 第三层 | 消费者防重          | 幂等判断 + 消费记录表，确保不重复处理                                          |
| 第四层 | 兜底对账           | 定时任务扫描流水、快照汇总与明细是否一致，不平告警                                     |

**（4）汇总TAB查询流程**

用户打开汇总页面

**（5）事件驱动跨域联动**

```java
// 核销审核通过 → 写入本地消息表 → 事务提交后发布事件
@Service
public class WriteoffService {
    @Autowired private ApplicationEventPublisher publisher;

    @Transactional
    public void approveWriteoff(Long writeoffId) {
        // 1. 更新核销单状态 = 已核销
        // 2. 更新金额快照和流水
        // 3. 写入本地消息表，状态 = INIT
        // 4. 发布领域事件；监听器在事务提交后处理
        publisher.publishEvent(new WriteoffApprovedEvent(writeoffId));
    }
}

// 使用模块监听，更新使用金额状态
@Component
public class WriteoffApprovedListener {
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    @Async
    public void handle(WriteoffApprovedEvent event) {
        // 1. 根据本地消息表做幂等判断
        // 2. 更新使用模块金额状态（释放/调配）
        // 3. 消费成功后更新消息状态 = DONE
    }
}
```

不用 MQ，只用 Spring 自带的 `@TransactionalEventListener` 和 `@Async`。事件监听必须在事务提交后执行，避免主事务回滚但异步逻辑已消费的问题；本地消息表用于进程重启后的补偿重扫。

**（6）审批流程设计**

在现有审批功能基础上抽象审批规则接口：

```java
public interface ApprovalRule {
    /** 判断当前审批规则是否适用 */
    boolean matches(ApprovalContext context);
    /** 返回审批人列表 */
    List<String> getApprovers(ApprovalContext context);
}
```

按部门+金额层级实现不同规则：

- `StrategyBrandDeptRule`：战略厂牌事业部审批链路
- `OperationCenterRule`：运营中心审批链路
- `MoneyTreeRule`：摇钱树事业部审批链路

#### 1.3 方案风险（必填）

| 风险                           | 影响             | 应对措施                              |
| ---------------------------- | -------------- | --------------------------------- |
| 金额快照与主表数据不一致                 | 汇总数据不准确        | 定时对账任务 + 告警 + 自动补偿                |
| 流水表持续增长                      | 查询变慢、存储膨胀、备份变慢 | 按账期保留近 12\~24 个月在线数据，历史流水归档到年度归档表 |
| 结转重复执行或中断                    | 期初余额重复、跨年余额错误  | 结转批次表 + 唯一幂等键 + 可重试状态机            |
| 历史归档数据被修改                    | 审计链路不可信        | 归档表只读，历史调整通过当前账期反向流水处理            |
| Spring `@Async` 异步事件丢失（进程崩溃） | 跨域状态未更新        | 引入本地消息表落盘 + 定时重扫                  |
| `FOR UPDATE` 行锁在高并发下竞争       | 使用申请响应慢        | 短事务设计，锁持有时间控制在毫秒级                 |
| 金额计算口径理解偏差                   | 金额字段计算错误       | 统一的计算口径文档 + 单元测试覆盖边界场景            |

#### 1.4 局限性（必填）

- 金额最终一致性：跨域操作（如核销→释放）有短暂延迟（毫秒\~秒级）
- 汇总快照表异步更新：汇总页面展示可能延迟数秒
- 流水归档后的历史明细查询需要按账期路由到归档表，查询实现比单表略复杂
- 一期若只预留归档能力、不启用自动归档，则仍需后续补充归档任务和运维监控
- 不适合写并发极高的场景（行锁竞争），但资金池业务场景日均操作量级下无压力
- Spring Event 不支持跨进程（单体下不需要），若未来拆微服务需改为 MQ

#### 1.5 硬件和云资源（选填）

基于现有 PMS 资源，无额外硬件需求。仅新增 MySQL 表。

### 方案二：纯数据库事务方案（传统CRUD）

#### 1.1 方案概述关键点（必填）

不使用事件驱动和快照表，所有金额计算依赖数据库 SQL 实时聚合，通过事务和行锁保证一致性。

#### 1.2 概要设计（必填）

- 每次查询金额时通过 SQL 实时计算（SUM + 子查询 + 多表 JOIN）
- 金额变更操作在同一个 `@Transactional` 事务中完成，加 `FOR UPDATE` 行锁
- 审批逻辑在 Service 层 if-else 硬编码
- 汇总页面查询时逐层聚合

#### 1.3 方案风险（必填）

- 汇总页面查询需 JOIN 10+表，大数据量下可能超时（>5秒）
- 金额计算分散在多处，口径维护困难
- 核销触发释放/调配等跨流程操作需长事务，死锁风险高

#### 1.4 局限性（必填）

- 查询性能瓶颈严重，汇总页面体验差
- 代码耦合度高，难以维护和扩展

***

### 方案三：CQRS + 读写分离 + 物化视图

#### 1.1 方案概述关键点（必填）

写操作保持领域建模保证一致性，读操作通过物化视图/冗余汇总表优化查询。

#### 1.2 概要设计（必填）

- 写模型：使用领域服务编排，事务保护金额变更
- 读模型：建多张维度汇总表，写模型提交后同步更新汇总表
- 导入导出使用异步任务

#### 1.3 方案风险（必填）

- 读写模型间存在短暂延迟
- 汇总表同步逻辑需维护，代码量比方案一大
- 没有事件驱动，跨子域操作仍耦合

#### 1.4 局限性（必填）

- 相比方案一，缺少事件驱动的解耦能力
- 比方案二复杂但收益有限

***

## 三、方案推荐

### 1. 方案优劣对比

| 维度     |   方案一：事件驱动   | 方案二：纯DB事务 |  方案三：CQRS  |
| ------ | :----------: | :-------: | :--------: |
| 金额一致性  | 跨域最终一致/同域强一致 |    强一致    | 写强一致/读最终一致 |
| 查询性能   |     ⭐⭐⭐⭐⭐    |     ⭐⭐    |    ⭐⭐⭐⭐⭐   |
| 实现可控性  |       中      |     高     |      中     |
| 代码可维护性 |     ⭐⭐⭐⭐⭐    |     ⭐⭐    |    ⭐⭐⭐⭐    |
| 审批流扩展  |     抽象接口层    |    硬编码    |  独立Service |
| 跨域解耦   | Spring Event |     无     |    直接调用    |
| 引入新中间件 |  无（Spring自带） |     无     |      无     |
| 适合未来演进 |  ✅ 子域可独立为微服务 |     ❌     |     部分     |

### 2. 推荐方案

**推荐方案**：方案一（领域驱动设计 + 事件驱动架构）

**推荐理由**：

1. **金额复杂度高**：资金池涉及10+种金额状态的交叉计算，DDD 子域划分让每个域专注自己的状态机，代码清晰可维护
2. **查询性能关键**：金额快照表保证汇总页面秒级响应，无需实时 JOIN 多表
3. **跨域联动天然适合事件**：核销自动触发释放、自动调配是典型的事件驱动场景，Spring `@TransactionalEventListener` 即可实现
4. **不增加额外中间件**：不引入 MQ/ES，Spring 自带事件机制 + MySQL 本地消息表即可
5. **演进友好**：项目仍是单体重构，未来如需要可平滑将某个子域拆为独立微服务

***

### 3. ES 搜索引擎必要性分析

#### 3.1 数据量预估

PMS 是企业内部 B2B 系统，资金池数据来自厂牌商务备案→使用→核销链路：

| 数据           | 月增量预估   | 年总量预估  |
| ------------ | ------- | ------ |
| 备案单          | 几百\~几千条 | \~5万条  |
| 使用单          | 几千条     | \~10万条 |
| 核销单          | 几千条     | \~10万条 |
| 资金来源明细（外部引入） | 几千行     | \~10万行 |

**数据量级在百万级以内，MySQL 完全能扛。**

#### 3.2 查询模式分析

| 查询类型  | 特征                      | 数据源            |
| ----- | ----------------------- | -------------- |
| 汇总TAB | GROUP BY + SUM 聚合，多维度筛选 | 汇总快照表（几千行维度数据） |
| 列表查询  | 精确匹配（单号、状态）+ 时间范围       | 各主表（分页查询）      |
| 搜索筛选  | 下拉选择 + 输入匹配（精确/前缀匹配）    | MySQL LIKE / = |

**所有场景均为结构化查询，没有全文搜索或模糊大范围匹配需求。**

#### 3.3 引入 ES 的成本与风险

| 维度    | 说明                          |
| ----- | --------------------------- |
| 集群成本  | 至少 3 节点 ES 集群，增加硬件和运维投入     |
| 数据同步  | 需维护双写或 Canal 同步，增加复杂度       |
| 一致性问题 | ES 写入成功 vs MySQL 失败，金额可能对不齐 |
| 运维成本  | 集群监控、索引维护、故障恢复              |
| 实时性   | ES 写入有秒级延迟，用户操作后需立即看到变化     |

#### 3.4 结论

**不需要 ES。** 方案一中的金额快照表和汇总快照表已经解决了查询性能瓶颈：

- 汇总查询只查 1 张几千行的汇总快照表，MySQL 毫秒级返回
- 列表查询走主表索引分页，百万级数据无压力
- 无需全文搜索或模糊匹配需求

如果未来数据量暴增（月增量达到 10 万+），可考虑以下优先级方案：

1. **Redis 缓存**热点汇总查询
2. **MySQL 分区表**（按时间分区）
3. **ClickHouse/Doris** 列式存储（适合 OLAP 聚合）

**而非 ES（ES 擅长全文搜索，不擅长结构化聚合查询）。**

## 附录 — 技术方案撰写标准

### 设计原则

1. **金额操作必须使用数据库事务 + 行锁**：防止并发场景下的超用
2. **跨域联动优先使用事务提交后事件**：不直接跨 Service 调用，避免循环依赖；监听逻辑必须在主事务提交后执行
3. **快照表优先于实时计算**：涉及金额汇总的查询统一走快照表
4. **幂等性是基本要求**：所有异步事件消费者必须支持幂等
5. **对账兜底**：必须有定时任务检查数据一致性

### 命名规范

- 数据库表前缀：`fund_pool_`
- 备案单号规则：`BA` + YYMMDD + 6位顺序码
- 使用单号规则：`SY` + YYMMDD + 6位顺序码
- 核销单号规则：使用单号 + `_` + 自增数字
