# 需求拆解心法与通用提示词

你是资深架构师兼交付教练。请基于我提供的项目文档，输出“可执行的小任务拆解方案”，用于开发-review-测试循环。


## 一、拆解心法（哲学层）

核心原则：先切决策点，再切交付闭环，最后切验证边界。

- 决策点优先：优先识别 if/else、规则分支、角色差异、状态流转。
- 闭环最小化：每个任务都应可独立开发、评审、测试、回滚。
- 验证先行：拆解时就定义“如何证明完成”。
- 风险前置：先低耦合高确定性，后高复杂高风险。
- 兼容兜底：历史数据、默认值、空值、降级逻辑独立成任务。
- 可追踪性：每个任务都要有唯一输入、唯一产出、唯一验收标准。

## 二、通用拆解步骤（方法层）

1. 抽实体：对象、字段、枚举、状态、接口。
2. 抽决策：业务分支、适用矩阵、例外规则。
3. 抽约束：校验、互斥、默认值、兼容策略。
4. 抽公式/算法：计算逻辑、边界、舍入、优先级。
5. 抽流程：时序、前后置依赖、读写路径。
6. 映射任务：按“一个行为变化 = 一个任务”进行切片。

## 三、万能拆解提示词（完整版）

```text
你是资深架构师兼交付教练。请基于我提供的需求文档和项目代码，输出“可执行的小任务拆解方案”，用于开发-review-测试循环。

请不要只做业务拆解，还要完成项目落点分析：指出项目中哪些文件、类/函数、接口、配置、SQL、测试需要修改/新增/删除，并尽量精确到当前代码的起止行号。

【拆解目标】
- 不一次性实现全部需求
- 采用小步快跑，每个任务可独立开发、评审、测试、回滚
- 优先降低风险与耦合，保证持续可交付
- 让开发者拿到任务后能直接知道“改哪里、怎么改、如何验收”

【拆解原则】
1) 每个任务只包含一个核心行为变化（一个决策点或一个规则分支）
2) 每个任务都有明确输入、输出、影响范围、验收标准
3) 每个任务必须可独立测试（至少：正向/边界/回归）
4) 兼容性（历史数据、默认值、空值）必须单独成任务
5) 先做基础能力与低风险任务，再做复杂公式与高风险任务
6) 标注任务依赖关系与可并行关系
7) 每个任务必须包含项目变更清单，明确新增/修改/删除的具体位置

【代码定位要求】
1) 先阅读项目目录、关键模块、现有接口、服务、实体、Mapper/DAO、配置和测试文件
2) 所有变更点必须使用以下格式描述：
   - 操作类型：新增/修改/删除
   - 文件路径：从项目根目录开始写相对路径
   - 代码位置：类名/函数名/接口名/配置项名
   - 行号范围：如 L35-L58；单行写 L35
   - 变更原因：对应哪条需求或规则
   - 预期改动：用 1-3 句话说明要改成什么
3) 新增文件没有行号时，写“新增文件”，并说明建议放置目录；在已有文件中插入代码时，写“插入到 Lxx 之后/之前”
4) 删除逻辑必须给出删除范围、删除原因、兼容影响和回滚方式
5) 如果当前信息无法确定行号，必须标注“待代码检索确认”，并说明还需要查看哪些文件，不能用空泛描述替代
6) 行号必须基于当前项目代码，不要编造不存在的文件或行号

【请按以下结构输出】
A. 文档关键要素提取：
- 实体/字段
- 枚举/状态
- 业务决策点
- 约束与校验
- 公式与算法
- 兼容策略

B. 项目变更点总览：
- 需要新增的文件/类/接口/表字段/配置/测试
- 需要修改的文件/类/函数/接口/SQL/配置/测试（带行号范围）
- 需要删除或下线的逻辑/字段/配置（带行号范围）
- 需要重点关注的兼容点、数据迁移点、回滚点

C. 任务分层拆解（按阶段）：
- 阶段名（目标）
- 任务列表（T1, T2...）

D. 每个任务卡片模板（逐条输出）：
- 任务ID：
- 任务名称：
- 目标行为（只写一个变化点）：
- 范围（涉及模块/接口/字段）：
- 前置依赖：
- 项目变更清单：
  - 新增：
    - 文件路径：
    - 代码位置：
    - 行号/插入位置：
    - 预期改动：
  - 修改：
    - 文件路径：
    - 代码位置：
    - 行号范围：
    - 预期改动：
  - 删除：
    - 文件路径：
    - 代码位置：
    - 行号范围：
    - 删除原因与兼容影响：
- 实现要点（3-5条）：
- Review检查点（3-5条）：
- 测试用例（正向/边界/回归）：
- 完成定义 DoD：
- 风险与回滚方案：

E. 执行建议：
- 推荐迭代顺序（为什么）
- 哪些任务可并行
- 每轮迭代建议时长（如 0.5 天/1 天）

【输出要求】
- 任务颗粒度要小，避免“大而全”
- 优先输出可直接开工的任务
- 避免空泛描述，尽量具体到字段/规则/公式/代码位置
- 必须给出文件路径和行号；无法确定时，明确写出待确认项和需要继续检索的范围
```

## 四、极速版提示词（30 秒）

```text
请结合需求文档和当前项目代码，把需求拆成可执行小任务，要求：
1) 一个任务只改一个决策点
2) 每个任务可独立开发-review-测试-回滚
3) 每个任务都给出：目标、范围、依赖、验收、测试（正向/边界/回归）
4) 每个任务必须指出项目落点：新增/修改/删除哪些文件、类/函数/接口/配置/SQL/测试，并给出具体行号范围（如 L35-L58）
5) 新增文件写建议路径；插入代码写插入到哪一行前后；删除逻辑写删除范围、原因、兼容影响和回滚方式
6) 历史兼容与默认值单独拆任务
7) 按低风险到高风险排序，并标注可并行任务
请输出“项目变更点总览 + 阶段 + 任务卡片”格式；如果无法确定行号，必须标注待代码检索确认，不能编造。
```

## 五、一句话心法

先把不确定性拆散，再把确定性交付。
