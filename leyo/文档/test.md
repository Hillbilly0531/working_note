## **1. 项目背景**



这个项目是一个面向团队内部使用的 SQL 审查工具，目标是把“SQL 规范检查 + EXPLAIN 分析 + 元数据辅助判断 + AI 建议”整合到一个本地可运行的 Web 工具里。



项目核心能力包括：



- 支持原始 SQL、MyBatis XML、MyBatis 模板片段输入
- 基于规则引擎做可复现的静态审查
- 可接只读库执行 EXPLAIN
- 支持 AI 辅助解释、格式化、建议生成
- 支持配置化 AI 提示词
- 支持复制/导出审查结果
- 支持打包为 exe，本地启动后自动打开浏览器

这个项目很适合用 Vibe Coding 来做，因为它同时具备以下特点：



- 需求变化快，而且很多细节只有在实现时才会暴露
- 既有后端、前端，又有本地打包、配置、测试、文档
- 很多事情适合 AI 提高速度，但又不能完全放权给 AI

所以它不是“让 AI 直接写完”，而是“让 AI 变成一个高效率、可约束、可回放的协作开发搭子”。



## **2. 这个项目里，我是怎么和 AI 沟通的**



### **2.1 先讲目标，再讲边界(opus4.6)**



这个项目里最有效的提问方式，不是“帮我做一个功能”，而是下面这种结构：



1. 先讲业务目标
2. 再讲范围边界
3. 再讲不允许动的东西
4. 再给出验收标准

例如这次“AI 提示词可配置 + 审查结果复制/导出”的需求，如果只说一句“加两个功能”，AI 很容易把“复制/导出”理解成导出提示词配置，或者改动 API 结构。



真正高效的表达方式是：



- 提示词要可配置，但复制/导出的是审查结果，不是提示词
- 不改 `/api/review` 的响应结构
- 不要编辑计划文件本身
- 待办顺序要按计划执行，并逐个推进

这类约束越清楚，返工越少。



### **2.2 把非目标说清楚**



这次实践里很明显的一点是：和 AI 协作时，非目标往往和目标一样重要。



例如下面这些限制，都是必须显式说出来的：



- 不允许修改计划文件
- 导出的不是 AI 提示词，而是审查结果 JSON
- 不改变既有 API 合同
- 只能把 AI 用于建议，不允许 AI 直接替代可复现规则
- 打包时不要带出数据库账号和 AI 配置，但要保留内置数据集

这些约束一旦缺失，AI 很容易做出“看起来合理，但业务上不对”的实现。



### **2.3 一次只推进一个逻辑块**



Vibe Coding 并不等于“一口气做完全部需求”。

这次实践里，更有效的是把复杂需求拆成稳定的工作块：



1. 先做数据层和迁移
2. 再做 AI 提示词读取与替换
3. 再做配置页
4. 再做审查结果复制/导出
5. 最后补测试、文档、打包

这样做有两个好处：



- 每一步都更容易校验对错
- 出问题时，定位会非常快

### **2.4 明确要求“验证后再宣布完成”**



如果不要求 AI 运行验证，它很容易在“逻辑上觉得没问题”时提前宣布完成。



这个项目里，比较有效的方式是：



- 改完后跑 `pytest`
- 出现失败先修复，再重新验证
- 打包改动后确认路径、`spec`、运行入口是否合理
- 再输出结论

这个习惯直接决定了结果是否可靠。



## **3. 这个项目里，哪些 skills 最有价值**



这里我不把 skill 当成“花哨插件”，而是把它理解成一套固定协作套路。

### **3.1**\`brainstorming\`



这是最值得固定使用的 skill。



它的价值不是“帮你发散创意”，而是强制你在写代码前把问题说完整：



- 当前项目上下文是什么
- 这次改动到底要解决什么问题
- 哪些是目标，哪些不是
- 有没有更轻的实现方式

这个项目最开始能稳定推进，很大程度上就是因为先形成了设计与边界，而不是直接让 AI 开写。



适用场景：



- 新功能设计
- 功能边界容易歧义的需求
- “看起来简单，其实细节很多”的改动

### **3.2**\`writing-plans\`



这个 skill 对应的核心价值是：把设计变成可执行计划。



这次项目里，“AI 提示词与结果导出”之所以推进顺畅，是因为最终不是一句模糊需求，而是一份带 todo 的实现计划，里面明确了：



- 要改哪些层
- 每层做什么
- 哪些字段和接口不能动
- 风险点是什么
- 测试和文档要补什么

这能显著降低 AI 的自由发挥空间，让实现更贴近预期。



### **3.3**\`verification-before-completion\`



这是把 Vibe Coding 从“写得快”拉回“交付稳”的关键 skill。



它对应的是一种纪律：



- 不靠主观判断说“已经好了”
- 一定要给出验证证据
- 先看测试，再说完成

这次项目里，测试在一次改动后曾因为 Windows 下临时 SQLite 文件句柄问题失败。

如果没有“先验证再结论”的意识，这种问题很容易被漏掉。



### **3.4**\`systematic-debugging\`



虽然很多时候我们会直接修，但真正高效的方式其实是系统化排障。



这个项目里体现得很明显的几个场景：



- 审查结果导出语义和提示词导出语义混淆
- SQLite 临时文件在 Windows 下清理失败
- 打包后静态资源、模板、数据库路径都和开发态不同
- 打包时要剔除敏感配置，又要保留内置数据集

这些问题如果不分层排查，很容易在一个点上来回反复。



### **3.5**\`requesting-code-review\`



这个 skill 的价值是：当一个逻辑块做完后，不要只看“能不能跑”，还要看有没有风险。



对这个项目而言，重点 review 点包括：



- 是否存在运行时空指针风险
- 是否把提示词和审查结果语义混淆
- 是否误把敏感配置打进安装包
- 是否引入前端交互误导

从项目经验上看，这一步很适合放在“功能完成但还没准备对外展示”之前。



### **3.6 Cursor 的模式能力：**\`Plan Mode\`**、**\`Agent Mode\`**、**\`Debug Mode\`



除了 skill 本身，这次项目里另一个很有价值的体验，是 Cursor 不同模式在不同阶段各司其职。



**####** \`Plan Mode\`



`Plan Mode` 最适合用在“需求还没完全定型”的阶段。



这次项目里，像下面这些需求如果直接进入实现，其实很容易返工：



- AI 提示词到底是写死、环境变量，还是做成可配置
- 复制/导出的到底是提示词，还是审查结果
- 打包时哪些数据要保留，哪些配置必须排除

在这种阶段，`Plan Mode` 的价值不是写代码，而是：



- 帮你把需求拆清楚
- 帮你识别边界和非目标
- 帮你提前暴露实现上的歧义
- 把模糊想法整理成可执行计划

从这次实践来看，`Plan Mode` 很适合放在“需求讨论”和“正式开工”之间，起到一个缓冲和澄清作用。



**####** \`Agent Mode\`



`Agent Mode` 是这次项目的主工作模式，适合真正进入落地阶段之后使用。



它的优势是：



- 可以直接读写代码
- 可以跨文件修改
- 可以跑测试、起服务、看日志
- 可以把前端、后端、文档、脚本联动起来一起推进



但也正因为它能力很强，所以更需要人为限制边界，否则就容易变成“能改很多，但不一定改得准”。



**####** \`Debug Mode\`



`Debug Mode` 最适合在“问题已经出现，但根因还不清楚”的时候使用。



这次项目里几个典型场景就很适合用这种模式：



- SQLite 临时文件在 Windows 下清理失败
- 打包后模板、静态资源、数据库路径和开发态不一致
- 服务启动了但浏览器未自动打开，或者日志不够明显
- 打包时既要排除敏感配置，又要保留内置数据集

如果这些问题一上来就直接改代码，很容易陷入“哪里报错改哪里”的补丁式开发。

而 `Debug Mode` 更适合先把现象、预期行为、最近改动和可能根因拆开，再决定怎么修。



#### **三个模式怎么配合**



如果把这次项目的模式切换总结成一句话，大概就是：



- `Plan Mode`：把问题说清楚
- `Agent Mode`：把方案做出来
- `Debug Mode`：把异常查明白

它们的关系不是替代，而是接力。



一个比较稳妥的节奏通常是：



1. 先在 `Plan Mode` 里澄清需求和边界
2. 再进入 `Agent Mode` 做分块实现
3. 一旦出现异常或测试失败，再切到 `Debug Mode`
4. 问题定位清楚后，回到 `Agent Mode` 修复和验证

这种模式切换，本质上是在减少“黑盒式一路写到底”的风险。



## **4. 这次 Vibe Coding 的有效工作流**



我总结下来，最适合这个项目的工作流是：



### **第一步：设计先行，而不是代码先行**



先写设计文档，明确架构、数据流、边界和判定原则。

尤其这个项目有一个很重要的原则：



> 能用代码稳定实现的，不交给 LLM 做阻断判断。



这句话本质上就是项目的技术总原则。如果没有先定这个原则，后面会很容易把 AI 用错地方。



### **第二步：计划化拆分，而不是一句话让 AI 自由发挥**



设计之后，把需求拆成 todo，并约束执行顺序。

这样 AI 就不是“自己决定先做什么”，而是按照你定义的里程碑推进。



### **第三步：实现时持续纠偏**



这一步是 Vibe Coding 和传统开发最大的不同。



因为 AI 很快，所以你可以一边实现一边修正表达：



- “不是这个意思”
- “复制的是审查结果，不是提示词”
- “不要改计划文件”
- “打包时不能带出账号配置”

这种即时纠偏，本质上是在不断收紧需求语义。



### **第四步：每完成一个块就验证**



不要等所有功能做完再一起看。

这次项目里，迁移、配置页、前端导出、测试、打包都是分块验证的。



这能显著降低后期联调成本。



### **第五步：把 AI 从“生成器”变成“协作对象”**



真正有效的 Vibe Coding，不是让 AI 替你做决定，而是：



- 让 AI 做实现和草拟
- 人负责定边界、做选择、抓风险
- 最终交付由人确认

这个角色分工非常重要。



## **5. 这次项目里，最值得分享的几个 AI 沟通案例**



### **案例 1：功能语义纠偏**



一开始“复制和导出”存在歧义。

如果不补充说明，AI 很容易把“可配置提示词”和“可复制导出结果”合并理解。



正确的沟通方式是直接补一句：



> 复制和导出的不是 AI 提示词，而是执行完审查以后的审查结果。



这句话看起来简单，但它决定了整个实现方向。



### **案例 2：把实现边界写进要求**



比如：



- 不改 `POST /api/review` 响应结构
- 不编辑计划文件
- 占位符替换不能用 `str.format`

这类要求如果只在脑子里默认，AI 是不知道的；只有明确说出来，它才能按你的边界实现。



### **案例 3：打包需求一定要讲清“保留什么、排除什么”**



“不要打包数据库账号和 AI 配置，但是要保留内置数据集”这句话很典型。



如果只说“不要打包数据库”，AI 可能连内置元数据也一起排除掉。

如果只说“保留内置数据”，AI 又可能把开发机上的 `sql_review.db` 一起带进安装包。



正确做法是明确区分：



- 什么是敏感运行时配置
- 什么是允许内置的静态示例数据

## **6. 这次实践里，我认为最重要的几点经验**



### **6.1 AI 最怕“默认推断”**



凡是你没有明确写出来的东西，AI 都会尝试推断。

而一旦进入推断，返工概率就会上升。



所以高质量提示词的本质不是华丽，而是：



- 目标明确
- 范围明确
- 非目标明确
- 验收明确

### **6.2 项目越复杂，越要让 AI 在结构内工作**



这个项目涉及：



- Python 后端
- Flask 路由
- SQLite 模型与迁移
- 前端模板和 JS
- 本地打包
- 测试与文档

这种复杂项目不适合“请 AI 随意重构”。

更适合：



- 先有设计
- 再有计划
- 最后按计划局部实现

### **6.3 测试不是收尾动作，而是沟通闭环的一部分**



很多人理解的 Vibe Coding 是“需求 -> 代码 -> 完成”。

但真正靠谱的闭环是：



`需求 -> 设计 -> 计划 -> 实现 -> 验证 -> 修复 -> 再验证`



只有这样，AI 才不是在“生成代码”，而是在参与一次完整的软件交付。



### **6.4 文档化会显著提升 AI 协作质量**



设计文档、实现计划、API 合同、需求边界，一旦写下来：



- AI 更容易理解上下文
- 人更容易做 review
- 需求变更更容易精准落位

所以文档不是额外负担，而是让 AI 更好工作的基础设施。



## **7. 如果下次再做，我会继续坚持的做法**



- 新需求先出设计，再进入实现
- 每个功能块都写清目标与非目标
- 尽量引用具体文件、路由、字段和符号
- 不允许 AI 自己扩需求
- 每个阶段完成后都跑验证
- 对易混淆语义第一时间纠偏
- 把“技能/工作流”固化成团队协作规范

## **8. 可直接对外分享的一句话总结**



这次 SQL Review Tool 的开发让我最大的收获不是“AI 写代码有多快”，而是：



> 真正高效的 Vibe Coding，不是让 AI 代替开发，而是让 AI 在清晰边界、明确计划和持续验证的框架里，成为一个高响应、低摩擦的协作型工程搭子。
