Project ContextSlide 02
Why This Project

它不是一个普通小工具，而是一个边界可定义的复杂工程。

这个项目同时覆盖规则审查、Explain 分析、元数据辅助、AI 建议、前后端联动、本地打包和配置治理，所以很适合拿来复盘 Vibe Coding 的真实价值。

场景定位
内部 SQL 审查工具
把 SQL 规范检查、Explain 分析、AI 建议和结果导出收拢到一个可落地的 Web 工具里。
能力组合
规则 + Explain + 元数据 + AI
既有可复现的规则引擎，也有需要自然语言解释和辅助判断的 AI 协作空间。
工程跨度
前后端 + 配置 + 打包 + 测试
需求不是单一模块变更，而是多个环节同时收口，天然暴露沟通与边界问题。
复盘价值
复杂，但可以被约束
它不是“让 AI 一把梭”的场景，而是“让 AI 在结构内加速”的最佳样本。
Collaboration PrincipleSlide 03
Core Rule

先讲目标，再讲边界。

最有效的提问方式，不是“帮我做个功能”，而是把目标、范围、禁止项和验收一起讲清楚。约束越清晰，返工越少。

需求表达不是描述功能，而是在定义 AI 可以工作的结构。
01
业务目标
先说要解决什么问题，而不是先说控件怎么长。
02
范围边界
明确这次改动覆盖哪里，不覆盖哪里。
03
禁止改动
把不能动的 API、文件和语义提前写出来。
04
验收标准
要求验证后再宣布完成，用结果闭环而不是靠感觉。
Communication MovesSlide 04
Four Moves

把复杂需求拆成 AI 能稳定接住的四个动作。

01
讲目标
先说业务意图，避免 AI 只盯着“表面功能”。
02
讲非目标
不说清非目标，AI 很容易补全成“看似合理”的错误实现。
03
分块推进
把需求切成稳定工作块，便于校验，也便于定位问题。
04
验证后完成
改完先跑验证，再说完成，把“逻辑上应该行”变成“证据上真的行”。
SkillsSlide 05
What Actually Helped

真正有价值的，不是“技能很多”，而是每个 skill 都在解决一种失控风险。

brainstorming
先把问题说完整
强制在开写之前说清上下文、目标、边界和更轻的实现路径。
writing-plans
把设计收成可执行计划
把模糊需求变成有顺序、有风险控制和有验证点的落地清单。
verification-before-completion
防止“以为完成”
要求改完先验证，再宣布完成，让交付从“写得快”拉回“交得稳”。
systematic-debugging
把排障改成分层定位
先拆现象、预期和根因，再修，不被补丁式开发牵着走。
Mode SwitchingSlide 06
Plan / Agent / Debug

不是一个模式包打天下，而是在不同阶段切换正确的工作方式。

Plan Mode
适合需求还没完全定型的时候。帮助澄清边界、非目标和实施顺序。作用是把模糊问题压缩成可执行结构。
Agent Mode
适合进入真正落地阶段后使用。能跨文件改代码、跑命令、联动前后端与文档。能力强，所以更需要人来约束边界。
Debug Mode
适合问题已经出现，但根因还不清楚的时候。帮助拆现象、预期、最近改动和可能根因。避免哪里报错就直接补哪里。
一条最稳的节奏：先澄清，再落地，出错后定位，再回到实现。
WorkflowSlide 07
Reusable Flow

最有效的 Vibe Coding，不是“写得快”，而是“始终在闭环里工作”。

设计

先确定原则、边界和核心判断，别直接让 AI 开写。

计划

把需求拆成顺序明确的任务，让实现路径变得稳定。

实现

进入 Agent Mode，按块推进，而不是一口气改完全部。

验证

每完成一个逻辑块就验证，让偏差尽早暴露。

修复

问题出现时切到 Debug Mode，先定位根因再修。

再验证

闭环之后再宣布完成，把交付建立在证据上。

Three CasesSlide 08
Cases That Matter

真正决定方向的，往往不是代码量，而是那些被及时纠偏的表达。

Case 01
功能语义纠偏
错误理解：把“复制/导出”理解成导出提示词。
正确表达：复制和导出的对象，是审查完成后的结果，而不是 AI 提示词本身。
Case 02
把边界写进要求
错误理解：默认允许 AI 改 API、改计划文件、自由替换实现。
正确表达：明确写出哪些接口、文件和实现边界不能动。
Case 03
打包时讲清保留与排除
错误理解：只说“不打包数据库”，很可能把该保留的内置数据也删掉。
正确表达：区分敏感运行配置和允许内置的静态示例数据。
TakeawaysSlide 09
Final Message
经验 01
AI 最怕默认推断
凡是没被明说的东西，AI 都会试图补全，而返工往往就从这里开始。
经验 02
项目越复杂，越要让 AI 在结构内工作
先有设计，再有计划，最后按计划局部实现，才能把速度转成稳定交付。
经验 03
验证不是收尾动作，而是沟通闭环的一部分
需求、设计、计划、实现、验证、修复，再验证，缺一环都会让协作质量下滑。
真正高效的 Vibe Coding，不是让 AI 代替开发，而是让 AI 在 清晰边界、明确计划和持续验证 的框架里，成为一个高响应、低摩擦的协作型工程搭子。

这也是这次 SQL Review Tool 项目最值得复用的部分：不是某个功能，而是一整套可持续的协作方法。
